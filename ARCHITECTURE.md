# Architecture

`ha-zbt2-led` is a Home Assistant custom integration. It turns the RGB LED on the Home Assistant Connect ZBT-2 into a light entity by sending the firmware's XNCP "set LED color" command over the serial link that ZHA already holds open.

## Layout

| Path | Role |
|---|---|
| `custom_components/zbt2_led/` | The integration Home Assistant loads. |
| `custom_components/zbt2_led/brand/` | Brand icons that HACS and Home Assistant display. Generated by `scripts/make_brand_icon.py`. |
| `tests/` | pytest suite run with `pytest-homeassistant-custom-component`. |
| `scripts/` | Maintenance scripts. |
| `docs/adr/` | Architecture decision records. |

## Modules

| Module | Role |
|---|---|
| `__init__.py` | Finds ZHA's config entry, checks the installed bellows version off the event loop, builds the controller and forwards the light platform. |
| `controller.py` | Follows ZHA's config entry state, owns the driver, and turns link errors into availability and repair issues. |
| `driver.py` | Plays effect programs one frame at a time: at most one frame per 0.5 s, newest program wins, retries failed frames, pauses and resumes with ZHA. |
| `effects.py` | Pure functions that turn an effect, colour, brightness and cap into a program of frames. No Home Assistant imports. |
| `light.py` | The `light.zbt2_led` entity: state, restore (including colour while off), effects and flash. |
| `zha_link.py` | The only module that touches private ZHA and bellows internals. See ADR 0001. |
| `config_flow.py` | Matches ZHA's radio path to the ZBT-2 hardware entry, checks LED support with inline errors, and offers the options. |
| `diagnostics.py` | Link and driver state for bug reports, with the serial number redacted. |

## How a colour reaches the LED

1. The entity builds a program for its state (`effects.py`) and hands it to the controller.
2. The driver sends the program's current frame through `zha_link.async_set_color`, which writes XNCP command `0x0F00` with a 3-byte RGB payload to bellows' EZSP object.
3. The firmware writes that colour to its LED manager's MANUAL layer. The network-status light lives on a lower layer, so it shows again only after the adapter restarts and loses the MANUAL colour.

## ZHA lifecycle

- The driver starts paused. It resumes only when ZHA's config entry reaches `LOADED`, and pauses on every other state.
- When ZHA loads, the controller checks the link, then asks the entity what to show. An off light under the default idle behaviour returns nothing, so the driver clears its program and leaves the status light alone. ADR 0002 records why.
- A ZHA reload resets the adapter, so the same path re-asserts the light after it.
- Reloading this integration (saving options) or re-adding the entity (an entity_id rename) does not reset the adapter. `LinkMemory` in `hass.data` carries the last frame time, whether the LED shows something this integration sent, and any standing repair across those.
- A ZHA start is recognised by ZHA's gateway object, which ZHA builds anew each time its config entry loads. `LinkMemory` keeps a weak reference to the gateway the LED was last brought in step with, so a ZHA restart counts as an adapter reset even when it happened while this integration was unloaded or its entity disabled.
- The controller follows one ZHA config entry. When that entry is deleted, the integration reloads itself, and setup raises `ConfigEntryNotReady` until a ZHA entry exists again. `async_setup` listens for ZHA config entries being added and reloads an entry waiting in setup retry at once, rather than leaving it to Home Assistant's retry, which backs off to 10 minutes.
- Removing the config entry deletes `LinkMemory` along with the repair issues.

## Boundaries

The integration depends on private ZHA and bellows internals, because no public API exposes the LED yet. That dependency is confined to `zha_link.py`, so a breaking upstream change is detected in one place and reported to the user as a repair issue instead of a crash. ADR 0001 records why.
